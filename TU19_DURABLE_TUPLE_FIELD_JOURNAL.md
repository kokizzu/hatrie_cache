# T-U19 Durable Tuple Field-Operation Journal

`hat/hatDataStructure` now provides an importable, bounded binary journal record for tuple field updates. It covers the existing `SET`, `SPLICE`, and `ADD_INT64` operations and can be replayed atomically through `TupleFieldOffsetCache.ApplyUpdates`.

## Why

Tuple field updates are useful as compact mutation batches, but a caller previously had to invent its own durable representation. The journal gives storage and replication code a deterministic record with:

- a versioned `TFJ1` header;
- a caller-supplied sequence number;
- bounded update count and encoded size;
- CRC32C corruption detection;
- deterministic encoding independent of Go map iteration;
- copied decoded values, so the input buffer can be reused safely.

The journal is a record format and replay primitive. It does not choose a file, WAL, replication, or checkpoint policy. The caller remains responsible for persisting records, ordering them, deduplicating sequence numbers, and deciding when a record is durable.

## Example

```go
record := hatDataStructure.TupleFieldUpdateJournal{
	Sequence: 42,
	Updates: []hatDataStructure.TupleFieldUpdate{
		{Index: 0, Kind: hatDataStructure.TupleFieldSet, Value: []byte("ready")},
		{Index: 1, Kind: hatDataStructure.TupleFieldAddInt64, Delta: 1},
	},
}

wire, err := record.MarshalBinary()
if err != nil {
	return err
}

decoded, err := hatDataStructure.UnmarshalTupleFieldUpdateJournal(wire)
if err != nil {
	return err
}

updatedCache, err := decoded.Apply(cache)
if err != nil {
	return err
}
_ = updatedCache
```

`MarshalTupleFieldUpdateJournal(sequence, updates)` is also available when the caller already has the sequence and update slice separately. JSON remains a fallback for compatibility by applying `encoding/json` to the exported `TupleFieldUpdateJournal` value; the binary format is the intended storage and transfer format for this record.

## Wire format and limits

The record encodes the magic, version, sequence, update count, and each update using unsigned varints where practical. Values are length-prefixed. The record ends with a four-byte big-endian CRC32C checksum over the preceding bytes.

The decoder rejects truncated records, unsupported operation kinds, negative indexes or ranges, duplicate field indexes, invalid varints, trailing bytes, checksum mismatches, more than `MaxTupleFieldUpdateJournalUpdates` updates, and records larger than `MaxTupleFieldUpdateJournalBytes`.

Sequence numbers are intentionally opaque to the data structure. This keeps the format useful for a WAL, a replication stream, or a checkpoint delta without silently imposing an idempotency policy.

## Benchmark

Measured on Linux/amd64 with an AMD Ryzen 9 5950X using the package benchmark target and `-benchtime=100ms -count=1`. The JSON comparison uses Go's standard `encoding/json` as the compatibility baseline.

| Operation | Binary ns/op | JSON ns/op | Binary speedup | Binary wire bytes | JSON wire bytes | Bandwidth reduction | Binary B/op | JSON B/op | Binary allocs/op | JSON allocs/op |

| Marshal | 109.6 | 727.1 | 6.63x | 29 | 272 | 89.3% | 32 | 320 | 1 | 2 |
| Unmarshal | 199.7 | 4932 | 24.70x | 29 | 272 | 89.3% | 304 | 968 | 3 | 13 |

Raw benchmark output is generated by `make benchmark-chg20-tuple-journal` in the feature worktree. The binary format is the default recommendation because it reduces CPU time, allocations, and transfer/storage size for this workload. JSON is still useful for inspection, interoperability, and gradual migrations.

## Verification

The focused test suite covers round trips, atomic application, deterministic encoding, input-buffer isolation, checksum corruption, malformed records, negative indexes, and duplicate indexes. Race, vet, package, and benchmark checks are run by the repository Makefile targets for T-U19.
